# Travel data contract

Read the generated `trip-data.json` for the complete container shape and `scripts/validate.mjs` for executable constraints. Keep empty containers; do not import legacy upstream canonical schemas.

- `metadata.tripId`: unique `[A-Za-z0-9_-]` identifier, max 100 characters, unchanged for the life of a trip. `metadata.title` is the page title; optional `metadata.timeZone` is a known IANA timezone for Today highlighting.
- `trip`: `status: draft`, `startDate`, `endDate` as real `YYYY-MM-DD` dates, `dayCount`; countries as `{code,nameZh,nameEn}` plus `primaryDestinationCountries`, `citiesAndAreas` and `routeSummary`. Domestic trips use `primaryDestinationName`. An undated draft uses null start/end and null day dates, never fictional dates.
- `days`: sequential `{day,date,title,locations:[],schedule:[]}`. Schedule items have stable `id`, `time` (`HH:MM` or `待确认`), `type`, `text`; use `placeId`/`placeIds` and `ticketIds` only for existing records.
- `places`: `{id,name,nameZh?,localName?,address?,cityOrArea?,countryCode?,geo?,navigation?}`. Country/region is a two-letter uppercase code. Coordinates are `{lat,lng,coordinateSystem?,source?}`; supported systems are `WGS84`, `GCJ02`, `unknown`. Known systems require a source. Unknown/legacy coordinates remain usable for the schematic but are not assumed precise for external navigation. Navigation is `{provider?,services?:{google?:{url?,placeId?},amap?:{url?,placeId?},apple?:{url?},kakao?:{url?,placeId?},yandex?:{url?,placeId?}}}`. Preserve legacy `navigation.url` and `googleMapsUrl`. Google `query` and Apple `q` must show a readable local name and address when available; precision coordinates serve the route map, Apple `ll`, or the no-name fallback. Never bulk-write pure latitude/longitude search URLs into `trip-data.json` as verified place URLs; see [display-and-navigation.md](display-and-navigation.md) for supported URL/fallback behavior.
- `ticketPlanning.items`: `{id,day,name,requirement,document?}`; PDF document is `{url:"assets/tickets/<file>.pdf",type:"application/pdf",label}`. Tickets may also be referenced from flights/stays. Keep the source PDF unchanged. The build generates a same-name PNG first-page preview behind the same authentication; `#ticket-dialog` displays it with zoom and retains an original-PDF link because mobile Chromium and WebKit can block PDF `iframe` content. Narrow-screen acceptance must confirm the ticket image is actually visible.
- `flightJourneys`: `{id}`; `flights`: `{id,journeyId,sequence,airline:{name},flightNumber,departure,arrival}`. Each endpoint has `airportCode,city,date,time,utcOffset` (`±HH:MM`). Use actual local times and date-specific UTC offsets; arrival must follow departure in UTC. For missing flight details use a journey with `placeholder:true,status:"pending",missingFields:[]` and no invented segment.
- `groundTransport.rentalCar`: company, vehicle `{example,class}`, price `{currency,payAtCounter}`, rentalPeriodDays, insurance array, pickup/dropoff `{date,time,utcOffset,location,address}` and appropriate return instructions. Keep rentalChecklist, drivingNotes and drivingReferenceLinks arrays. If required details are not supplied, keep rental disabled and record the gap rather than fabricate an active rental.
- `preTrip.packingItems`: explicit user tasks `{id,text,completed}`. In D1 these seed a new trip once; later source changes do not overwrite travelers' live checks. Apply later task changes through the shared UI/API.
- `accommodations`: `{id,name?,placeId?,status?,checkIn?,checkOut?,checkInTime?,checkOutTime?,roomType?,address?,price?,confirmationNumber?,cancellationPolicy?,ticketIds?,missingFields?,demo?,navigationNote?}`. Status is `pending`, `unconfirmed`, or `confirmed`; legacy omitted status is pending. Non-pending records require name, place reference, room type and valid check-in/out dates. Pending records allow null dates. Any provided date/time is validated; checkout must follow check-in. Price is `{currency,amount}` with nonnegative numeric amount. References must exist. `days[].schedule[].accommodationId` links a stay. `flightJourneys[].ticketIds` links credentials and flight endpoints may include `placeId`.
- `config.modules`: six required booleans `flights,overview,itinerary,todo,driving,ledger`, plus optional `accommodations`. When omitted, accommodation visibility follows whether records exist. `config.persistence` is `{mode:"d1",apiBase:"/api/trip",sharedCollections:["todos","tickets","ledger"]}`. Local language/map preferences never enter shared collections.
- `config.language`: optional `zh-CN` or `en`. `translations`: optional original-string → `{en?,"zh-CN"?}` display mapping. Keep technical IDs and original data unchanged. `config.demo` enables fictional-demo notices; `demoNavigationPlaceIds` requires demo mode and valid place references. Omit both from real trips.

For enabled maps, fill `map.region` or `map.regions` with region IDs and country codes; `map.places` has `{id,name,geo:{lat,lng},countryCode}`; `routes` and `dailyRoutes` have `{day,placeIds:[...]}`. Only use confirmed coordinates. If pending, retain the itinerary and report why the map remains unavailable. `mapMode` stays `template-auto`. The builder owns `routeMap` and `metadata.assets.routeMaps`. Preserve those derived fields during updates so previous regional template choices can be reused.

Maintain a private, small source index (source filename/page or user correction → affected field/record) for material ambiguity. A resolved correction replaces the relevant fact; it does not justify overwriting unrelated records or importing private extraction notes into the site.

Rental pickup/dropoff may reference a canonical `placeId`. Without it, navigation uses the supplied location/address and optional `countryCode`; an unknown country requires explicit map selection.
